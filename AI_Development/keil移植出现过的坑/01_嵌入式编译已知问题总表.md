## §1 构建系统 / 工具链层

### 1.1 F5 编译报 'cube' command is not available in current context (PATH not set)

- 根因：cube-cmake（build-cmake 扩展里的 Rust 包装器）依赖 PATH 中的 cube CLI；
  移植/生成的工程未做 Project Setup 注册 → 扩展环境注入缺失 → cube-cmake 裸奔
- 修复：VSCode Ctrl+Shift+P → STM32Cube: Configure/Project Setup → 选芯片 →
  Toolchain: GCC → Finish；之后 F5 通过
- 裸终端构建：先 export PATH 注入两个目录再跑 cube-cmake --build：
  - core 扩展 resources\binaries\win32\x86_64（cube.exe）
  - build-cmake 扩展 resources\cube-cmake\win32\x86_64（cube-cmake.exe）
- 快速判定法：手动注 PATH 跑 cube-cmake --build，成功=工程健康、病在扩展激活层；
  失败=工程真有编译错误
- 注意：GDB Server 本身不编译任何东西，别把它当"编译方式"

### 1.2 configure 过 ≠ 能编（真正的坑在 build 阶段）

- cmake --preset 只检查 CMake 语法和工具链；源文件缺失/宏错误/类型错误全部要等
  cmake --build 才暴露
- 用户报"CMake 生成失败"时，先跑 `cmake --build build/<preset>` 区分阶段
- 验证移植必须跑到出 .elf + Memory region 占用表为止（无板也能做）

### 1.3 CMake 工程名/目标名不能用中文

- 报 "reserved or not valid"，必须 ASCII 名（如 EXTI_test）

### 1.4 改 CMakeLists.txt 后必须重新 configure

- 直接 cmake --build 用的还是旧 build.ninja（残留旧链接标志）。
  先 cmake --preset Debug 再 build，否则改动不生效

### 1.5 nano.specs 重复添加 → 链接器 fatal error

- 报 `attempt to rename spec 'link' to already defined spec 'nano_link'`
- 根因：cmake/gcc-arm-none-eabi.cmake 工具链文件已带 --specs=nano.specs nosys.specs，
  根 CMakeLists.txt 又加了一遍
- 修复：删重复项；加 specs 前先读工具链文件确认

## §2 Keil→GCC 移植层（keil2cubevscode.ps1 脚本配套坑）

### 2.1 启动文件是 ARMCC 语法（GCC 编不了）

- 特征：报错集中在 startup .s，文件内是分号注释 + AREA 指令
- 修复：从 CubeMX 固件仓库拷 GCC 版：
  ~/STM32Cube/Repository/<固件包>/Drivers/CMSIS/Device/ST/STM32Fxxx/Source/Templates/gcc/
  拷到 CORE\（建议加 _gcc 后缀），填入 cmake/stm32cubemx/CMakeLists.txt 的 MX_Startup
- GCC 版特征：含 ".syntax unified" 和 __attribute__
- 先查再拷：V3.5 标准外设库老工程 startup/ 下常自带 gcc_ride7/ 目录，有就直接用
- F103 后缀速查：x6=低密度 / xb=中密度(RB 128K) / xe=高密度(RC/VC 256K, RE 512K) /
  xg=1M / 互联型(105/107)=xc。VCT6 用 startup_stm32f103xe.s + STM32F10X_HD

### 2.2 正点原子 CORE 缺 GCC 版 CMSIS 头

- 报 core_cm3.h 找不到 cmsis_gcc.h
- 修复：从固件仓库 Drivers\CMSIS\Include\ 拷 cmsis_gcc.h + cmsis_version.h
- 版本判定：CMSIS 1.x（V3.5 库自带）__GNUC__ 分支自成一体**不需要**补；
  只有 CMSIS 3.x/5 系（core_cm3.h 引用 cmsis_compiler.h）才补——别把 3.x 流程套 1.x

### 2.3 __asm void MSR_MSP 是 ARMCC 专属语法

- 修复为 GCC 内联汇编：
  void MSR_MSP(u32 addr) { __ASM volatile("msr msp, %0" : : "r" (addr) : "memory"); }
- 同族地雷：WFI_SET / INTX_DISABLE / INTX_ENABLE 若也是 __asm void 写法需同样改写
- 通用法：全局搜 __CC_ARM，确认每处都有 __GNUC__ 等价分支

### 2.4 GCC 14 把三类警告升级为默认错误（老 Keil 代码必炸）

- 典型报错：error: passing argument N of 'xxx' from incompatible pointer type
- 受影响：-Wincompatible-pointer-types / -Wimplicit-function-declaration / -Wimplicit-int
- 修复：cmake/stm32cubemx/CMakeLists.txt 的
  target_compile_options(stm32cubemx INTERFACE ...) 加：
  -Wno-incompatible-pointer-types -Wno-implicit-function-declaration -Wno-implicit-int
- 等效 Keil 时代宽松行为，不碰固件源码；建议写进移植脚本生成模板

### 2.5 脚本生成的 .ld 文件 Flash/RAM 始终为 0KB

- 脚本从 .uvprojx XML 读内存失败输出 0K 占位值；不要改脚本（硬编码只适用一个芯片）
- 每次移植后手动改 .ld。按芯片查表，勿套 H743 值：
  H743IITx = Flash 0x08000000/2048K，RAM 0x20000000/128K
  F429IGT6 = Flash 0x08000000/1024K，RAM 0x20000000/192K
  F103VCT6 = Flash 256K / RAM 48K；F103RCT6 = 256K / 48K
- 宏与启动文件也要匹配系列（F4 用 STM32F429xx + startup_stm32f429xx.s）

### 2.5b 脚本生成的 TARGET_FLAGS 是 -mcpu=cortex-m0（U5 实测新坑，2026-09-27）

- 位置：`cmake/gcc-arm-none-eabi.cmake` 第 47 行 `set(TARGET_FLAGS "-mcpu=cortex-m0 -mthumb")`
- U575 是 Cortex-M33，按 m0 编译后 CMSIS 的 `__LDREXW/__STREXW`（M0 无独占访问指令、
  该 CMSIS 路径只给 M3+ 定义）在 ATOMIC_SET_BIT 宏里 implicit declaration → GCC 14 升级为错误
- 症状迷惑点：报错点全在 hal_uart.c 等 HAL 驱动的 ATOMIC_xxx 宏，看似"又没开模块"，
  实际根因在 CPU 架构标志；用 ninja 的 compile command（`ninja -t commands` 或看错误上方
  完整命令行）核对 `-mcpu=` 即可一锤定音
- 修复：`set(TARGET_FLAGS "-mcpu=cortex-m33 -mthumb -mfpu=fpv5-sp-d16 -mfloat-abi=hard")`
  + 重新 configure。Test_Project 当年能编过是因为当年没编 uart/i2c 这类用 ATOMIC 宏的驱动
- 以后遇到新系列迁移，TARGET_FLAGS 与芯片内核核对表：F1/F4=cm4、H7=cm7、U5/H5=cm33
  （U5 hard-float 用 fpv5-sp-d16；不开 FPU 也可 -mfloat-abi=soft）

### 2.6 多 target 的 uvprojx：脚本只读第一个 target

- Keil 工程多 target（如 Flash=F103RB / CpuRAM=F103ZE）时，脚本按第一个 target
  生成 Device/宏/内存 → 真板不符则三件套全错（宏 MD/HD、.ld 大小、调试 device）
- 移植前必查：解析 uvprojx 每个 <Target> 的 <Device>+<Define>，与真板核对
- 判定依据：it.c 里 HD-only 中断（TIM8/UART4/TIM5）+ 用户外设号 + 芯片后缀

### 2.7 空壳"影子头文件"劫持系统头

- 症状：uint8_t/uint32_t 全部未定义、memset 隐式声明，错误横跨几十个不相关文件
- 根因：-I 路径目录下出现 0 字节的 stdint.h/string.h（VSCode 里误点"创建文件"），
  -I 目录优先于工具链系统头，尖括号引号通杀
- 修复：删空文件（0 字节零损失）。诊断：find + stat 按 mtime 找不属于原始包时刻的文件
- 预防：include 路径目录里永远不该出现与系统头同名的文件

### 2.8 GBK 中文注释乱码（用户要求：移植后不留中文注释）

- VSCode 打开乱码 = GBK 编码；GBK 源文件 read_file 会当二进制（用 iconv 读）
- 清除：状态机脚本只删含非 ASCII 的注释，字符串/字符字面量绝不触碰
- 只读属性文件：bash 内联 powershell 的 $_ 会被吞 → 写成 .ps1 再 -File 执行
- 验证三板斧：ninja 全量重编通过 + grep -rlP '[^\x00-\x7F]' 零残留（退出码要用
  $(...) 捕获，管道后 $? 是 head 的）+ 抽查人工确认
- 副作用：文件变 UTF-8+LF，Keil AC5 旧副本会反向乱码——两侧目录保持独立

### 2.9 五类手动适配（勘误手册 §3）

- uCOS-II：换 GCC 版 OS_CPU_A.s + 核对栈方向与 GCC ABI + OS_TICK_PER_SEC 对齐 SysTick
- Keil .lib 不能链接：需同版本同 -mcpu/-mthumb 的 GCC .a（IMPORTED 库接入）
- .sct 多分区：手动转 .ld（普通工程用脚本通用 .ld 即可）
- 汇编语法：UAL→GAS 对照（AREA→.section、PROC/ENDP→省略、EXPORT→.global、
  IMPORT→.extern、DCD→.word、ALIGN 4→.align 2，GAS 参数是 2 的幂）；
  推荐直接找 ST 官方 GCC 版替换而非逐行转换
- ps1 脚本：必须 UTF-8 with BOM + CRLF，否则中文 Windows 下解析炸

### 2.10 其他脚本配套知识

- launch.json：cortex-debug 的 serverpath 必须绝对路径（裸名报 spawn ENOENT；
  which JLink.exe 找到的是 JDK jlink，极易误判）；armToolchainPath 必填；
  preLaunchTask 对应 tasks.json label；ELF 路径匹配 preset 的 binaryDir
- 提交版 settings.json 只写裸名 JLinkGDBServerPath，本机差异用
  settings.local.json（已 gitignore）覆盖绝对路径——多机仓库友好
- flash.jlink 用相对路径 loadfile build/Debug/xxx.hex，task 设 cwd=workspaceFolder
- 链接 note "does not take linker garbage collection into account" 是提示不是错误，
  真错误在其上方第一行 error
- 新版脚本架构走 CMake Tools + cmake.cmakePath=cube-cmake 代理；旧工程升级 =
  删 .vscode 三件（tasks/settings/CMakePresets）后重跑脚本
- CubeMX CMake 输出是给 STM32CubeIDE 的；脚本只接受 Keil MDK-ARM V5 的 .uvprojx

## §3 CubeMX / HAL 配置层

### 3.1 手动用外设但 hal_conf.h 没开模块 → implicit declaration

- stm32xx_hal_conf.h 的 HAL_xxx_MODULE_ENABLED 控制头文件 include；
  CubeMX 只开图形界面里配过的模块
- 代码里手动用了外设（如 UART）而 CubeMX 没配 → 必须手动取消注释对应行，
  否则 HAL_UART_Transmit / UART_FLAG_TC 等全部未声明
- 常见漏项：HAL_UART_MODULE_ENABLED / HAL_USART_MODULE_ENABLED / HAL_TIM_MODULE_ENABLED
- 排查口诀：编译报 HAL_xxx 函数未声明，先看 hal_conf.h 模块开关

### 3.2 源文件没加进 CMake → 链接不到

- HAL 驱动：stm32xx_hal_uart.c + _ex.c 加进 cmake/stm32cubemx/CMakeLists.txt 的 MX_Sources
- 用户模块（usart.c/led.c/delay.c）：加根 CMakeLists.txt 的 target_sources 扩展区
- 覆盖脚本生成物同名路径的文件（如重写 iwdg.c）已被 MX_Sources 收录，勿重复添加
- it.c 集成：加 #include + 对应 IRQHandler 调用 HAL_xxx_IRQHandler

## §4 链接层

### 4.1 nosys 弱桩警告是正常的

- _close/_fstat/_isatty/_lseek/_read is not implemented and will always fail
  是警告不是错误，程序正常生成。但 _write 不重写 printf 就废（见 4.2）

### 4.2 printf 静默无输出（GCC newlib 用 _write 不是 __io_putchar）

- Keil MDK(ARMCC) 用 int __io_putchar(int ch)；GCC newlib 用
  int _write(int file, char *ptr, int len)
- 用错符号 = nosys 弱桩 always fail，链接不报错、程序能跑、printf 一个字不发
- 修复：提供 _write 强符号 → HAL_UART_Transmit(&handle, ptr, len, HAL_MAX_DELAY)
- 判定：arm-none-eabi-gcc → _write；armcc → __io_putchar。cube-cmake 环境永远是 GCC

### 4.3 printf %f 编译过但不输出

- newlib-nano 默认裁剪浮点支持。链接选项加 -u _printf_float
  （cmake/gcc-arm-none-eabi.cmake 的 CMAKE_EXE_LINKER_FLAGS，末尾常有预留注释行）
- 代价：FLASH 体积增大，仅确需打印 float 时启用

### 4.4 DRM 透明加密盘导致 ELF 损坏

- build 目录落在加密区 → .elf 被透明加密 → GDB 报文件损坏
- 修复：configure 时 -B 指向非加密盘，launch.json 的 ELF 路径同步改

## §5 代码层（写码/改码引入的编译与静默坑）

### 5.1 patch/Python 替换中 \r\n 转义陷阱（printf 字符串被劈断）

- C 源码里 printf("...\r\n") 的 \r\n 是字面量两字符，但传给 patch 工具或写进
  Python 替换串时被解释成真换行 → missing terminating " character / stray '\'
- 连踩 4 次实测；可靠修法：re.sub 用 lambda + chr(92) 拼反斜杠
- 预防：含 \r\n 字面量的改动优先用不含转义序列的 anchor 做 patch，
  或 write_file 整文件重写（对 C 字符串字面量处理正常）
- patch 后必须 grep 验证字符串完整

### 5.2 write_file 大块重写 typo 陷阱

- 长标识符易打入错误字符（= 多一个、@ 代替 x）
- 重写后必须 grep '[=@#\$]' 排除注释后查非法字符；或优先 patch 而非整文件重写

### 5.3 ISR 写 + 主循环读的变量缺 volatile（-O2 静默坑）

- Debug(-O0) 一切正常，-O2 后编译器把重复读取优化掉 → 接收完成标志永远看不到
- g_usart_rx_sta / g_usart_rx_buf 定义与 extern 都要 volatile；
  正点原子原版驱动同样缺，移植时顺手补

### 5.4 端口指针数组 const 方向写反

- const GPIO_TypeDef * → 传 HAL_GPIO_WritePin 报 -Wdiscarded-qualifiers
- 正确：GPIO_TypeDef *const（指针本身 const，指向内容可修改）

### 5.5 重名/残留文件类

- ISR 同时定义在 it.c 和用户 .c → 链接器重复定义；挪动时同步清理旧版本和 include
- 覆盖 HAL 弱符号的 MspInit 绝不能加 static（强符号需非 static 才能被链接器选中）
- USER CODE 区外的代码 CubeMX 重新生成会覆盖——用户代码永远写在 BEGIN/END 之间

## §2 移植脚本（U5 系列，2026-09-24 Test_Project 实测）

### 2.x 芯片宏写成 Keil 旧式名 STM32U575xI → CMSIS 报 "Please select first the target STM32U5xx device"
- 症状：stm32u5xx.h 落入 #error 分支，连锁报 RCC_PLL3FRACR undeclared / GPIO_TypeDef unknown 等几十个错（错误源头是宏，不是那些符号）。
- 根因：keil2cubevscode.ps1 把 uvprojx 的 Device 名（U575xI，xI=大容量后缀）直接抄进 cmake/stm32cubemx/CMakeLists.txt 的 MX_Defines_Syms；U5 的 CMSIS 头只认 STM32U575xx（注意 uvprojx 里 <Define> 反而是正确的 STM32U575xx，脚本没同步）。
- 修复：改 cmake/stm32cubemx/CMakeLists.txt 宏为 STM32U575xx，重新 configure。

### 2.y U5 的 .ld 占位不仅 0K，起始地址也是 0x00000000（比 H7/F4 的坑多一层）
- 症状：链接报 region FLASH overflowed，Region Size 显示 0 B；就算手填长度，origin=0x0 也不对。
- 修复：U575RIT6 填 FLASH 0x08000000/2048K、RAM 0x20000000/192K（786KB SRAM 中主 SRAM 192K @0x20000000）。

### 附带：CubeMX 新建 U5 工程时钟树 HSE 默认 16MHz
- 华清核心板实焊 12MHz 晶振，不改则实际 SYSCLK=120MHz 且波特率全歪。方案 A：M=3/N=40/P=1 → 160MHz，PLLRGE 必须 RANGE_0（VCO 输入 4MHz），VoltageScale 保持 SCALE1。
