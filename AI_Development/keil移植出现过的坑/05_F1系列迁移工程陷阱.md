# F1 系列迁移工程陷阱（F103RCT6 三连案沉淀）

> 案发：2026-08-19/20 · MiniSTM32 (F103RCT6, LQFP64)

## 1. SWD 断连真凶：`__HAL_AFIO_REMAP_SWJ_DISABLE()`（调试口自杀）

**症状签名：** 复位后立刻 halt 一切正常，程序一跑 SWD 就断；IDE 满屏 0xDEADBEEF、
"CPU could not be halted"。表象与 RDP 锁片一模一样，极易误判为硬件/芯片保护。

**根因：** CubeMX SYS→Debug 选 No_Debug 时，在 stm32f1xx_hal_msp.c 的
`HAL_MspInit()` 里生成 `__HAL_AFIO_REMAP_SWJ_DISABLE();` —— 固件启动几 ms 内
把 PA13/PA14 从 SWD 复用释放成普通 GPIO，J-Link 眼中目标凭空消失。
DEADBEEF 是调试器读不到内存时自己填的占位符，不是芯片里的数据。

**「我明明选了 Debug」的三层漏斗（用户会坚持说自己选了，他没记错）：**

1. **F1 系列 CubeMX 的 SYS→Debug 默认值是 No_Debug**（H7/F4/G0/L4 等新系列
   默认 Serial_Wire）。从 H7 流程迁移到 F1 时必查此项
2. **.ioc 只记录非默认值**。用户后来改回 Serial Wire 后 .ioc 里有
   `VP_SYS_VS_SWDIO_MODE.Mode=Serial_Wire_Debug` = 用户确实设置过且生效；
   不要因 .ioc「没有 No_Debug 字样」反推用户没遇到默认值
3. **hal_msp.c 不在 CubeMX 生成清单（.mxproject 无记录）**——它是
   keil2cubevscode 迁移/人工拷贝的正点原子模板文件，CubeMX 重新生成时
   **永远不会清理它**。地雷 = 「.ioc 设置正确 + 旧模板残留」复合车祸

**修复：** 注释掉 `__HAL_AFIO_REMAP_SWJ_DISABLE();` + .ioc 保持
Serial_Wire_Debug 双保险（重生成也不会再写入该行）。

**与真锁片的区分：** J-Link Commander 直连读选项字节 0x1FFFF800，
`FFFF5AA5` = RDP Level 0 无保护。VTref/DPIDR 三次稳定即排除硬件。

## 2. SysTick 延时陷阱：delay_us 末尾关 SysTick 不重开 → 后续延时≈0

**症状：** LED 看似「常亮」或闪得飞快；实际是 GPIO 极限速度翻转，人眼分辨不了。

**根因：** 正点原子式 delay.c 的 `delay_us()` 用 SysTick 忙等，末尾关 SysTick
且下次调用不重开。实测运行态 `SysTick->CTRL = 0x00000004`（ENABLE=0）、
LOAD 正常（0x25517F）、VAL=0 —— 第二次调用起延时直接≈0。

**修复（一行最小侵入）：** delay_us() 内写完 LOAD/VAL 后加
```c
SysTick->CTRL |= (1UL << 0UL);   /* 每次调用重新启动 SysTick */
```

**诊断手法：** 写 .jlink 脚本（复位 → 程序跑起来 → halt → mem32 读 SysTick
寄存器 0xE000E010/14/18），看 ENABLE 位即可定性。

## 3. 封装引脚缺失：抄大板 LED 映射在小封装上静默失败

**症状：** 程序正常跑、GPIO 驱动链路实测健康（CRL/ODR/IDR 全对），但灯不亮。

**根因：** led.h 抄了正点原子战舰/精英板（ZET6, 144脚）的 LED0=PB5/LED1=PE5；
RCT6 是 LQFP64，**物理上没有 PE 口**。编译不报错（寄存器地址存在），纯静默失败。

**规则：** 移植任何引脚映射前，先查 .ioc 的 `Mcu.Package`，确认目标封装有该端口。
MiniSTM32 最小系统板实测：LED0=PA8、LED1=PD2，低电平点亮。

## 4. 定时抓拍验证法（时序类 bug 的判决实验）

不靠肉眼，用定时 halt 抓寄存器做二分判决：复位 → sleep T → halt → 读 ODR。
例：500ms 翻转周期，T=450ms 时应 LED0 亮/LED1 灭，T=550ms 时反转。
翻转边界精确落在预期时刻 = 时序修复实锤。比示波器都快，零额外设备。

## 5. 验证脚本自身的坑

- J-Link mem32 输出行是**大写**十六进制地址（`4001080C = 0000A000`），
  解析时两侧都要 `.lower()` 再匹配，否则静默返回 None → 假 FAIL
- 本机 shell 里 `python` = hermes venv(3.11，无 pip)，`pip` 装到系统 3.13。
  跑 openpyxl 等三方库用全路径：
  `C:\Users\LENOVO\AppData\Local\Programs\Python\Python313\python.exe`
- 读寄存器值必须逐 nibble 核算，不要目测（本案 PE5 nibble 曾被目测误读，
  用 Python 逐位核算后纠正才得出「无 PE 口」的真结论）

## 6. 构建双树陷阱（Cube 插件工程通用）

顶层 `build/`（`cmake --build build` 默认目标）与 `build/Debug/`
（flash.jlink 烧录源、preset binaryDir）是**两份产物**。改码重编后必须
确认烧的是 build/Debug 的新 hex，否则烧进旧固件还以为修复无效。
